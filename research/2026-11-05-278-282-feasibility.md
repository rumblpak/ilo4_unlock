# 2026-11-05: Feasibility pass on v2.78-v2.82

Picking up where `2022-02-19-onto-277.md` left off. Goal: figure out, with
actual evidence instead of inference, what's realistically portable to
2.78-2.82 beyond the "dead" 278/279 scaffolds already in this repo.

Tooling note: no IDA/Ghidra available this round. Used a Python3 venv with
`pyelftools` + `capstone` for static analysis, plus `radare2` for function-level
auto-analysis, instead of the Windows/IDA workflow described in earlier notes.
The python2 build/patch toolchain (`build.sh`, `util/patch.py`, keystone) ran
inside a Debian bullseye Docker container (host has no python2).

## Reproducibility gate
Rebuilt 2.77/2.78/2.79 from genuine HPE binaries and confirmed each output
matches the `RESULT_SHA1` already recorded in `patches/*/config`. Toolchain
trustworthy.

## Structural findings across all six binaries (2.77-2.82)
- Bootloader is **byte-identical** across all six versions.
- Kernel is identical 2.77->2.81. 2.82's kernel differs by only 89 scattered
  bytes, all inside embedded build-path strings (e.g. `...newpatch\...` ->
  `...ilo4_282\...`) -- cosmetic, explains the 6-byte overall file-size delta
  for 2.82.
- `elf.bin` is a real (if "stripped") ARM32 ELF with per-task sections
  (`.health.elf.text`, `.ConAppCLI.elf.text`, `.restserver.elf.text`, etc.),
  each with a real `sh_addr`/`sh_offset` pair -- i.e. pyelftools alone gives
  the vaddr<->file-offset mapping per task that the original research notes
  got from IDA + `dissection.rb`. No need to run the Ruby/metasm tool.

## Signature bypass: confirmed portable to 2.80/2.81/2.82
Bootloader (`0x38BC`) and kernel (`0x1FBB0`) checks are byte-identical in all
six firmwares -- same patch applies unmodified. The userland AOB
(`02 80 83 E0 87 1E 00 EB 00 20 B0 E1 1D 00 00 0A`) was found as a **unique
single match** in every version:
- 2.80 @ file offset `0x964DFC`
- 2.81 @ `0x969A0C`
- 2.82 @ `0x96A240`

Independently re-verified (not just AOB match) by disassembling the
surrounding ~24 bytes in each version and confirming the exact same
instruction shape as 2.77's known-good check: `BL <verify>; MOVS R2, R0; BEQ
<skip>`. All three match 2.77's pattern exactly.

Built `patches/280`, `patches/281`, `patches/282` with **signature-bypass
only** (reusing the identical bootloader/kernel patches, new userland
offsets above). Verified via the full pipeline: extract -> patch -> repack,
`build.sh <ver>` run twice each confirming deterministic output, hashes
recorded as `RESULT_SHA1` in each `config`. 2.77 regression build reconfirmed
unaffected. `BINARY_URL` in each new `config` is a placeholder
(`TODO-VERIFY-HPE-DOWNLOAD-URL`) -- real HPE download links need to be found
before these are considered complete; never guessed per project policy.

These three are **not yet hardware-tested** and are deliberately scoped to
just the unlock mechanism -- no fan/health code is touched.

## Fan/health/ocsd/ocbb: real evidence of code loss, not yet a clean "C" verdict
- The `.health.elf.text` section is **707,912 bytes in 2.77** and drops to
  roughly **670,600-670,750 bytes in every one of 2.78-2.82** (stable across
  that range, not a progressive decline). ~38KB of code genuinely
  disappeared between 2.77 and 2.78 and nothing comparable happened again
  through 2.82.
- The CLI-side `health_ipc_call` wrapper (the function `patches/277/asm/fn_handler.S`
  calls into) is **byte-identical** in 2.77/2.78/2.79 at the correctly
  shifted offset -- the generic "send an IPC request to another task"
  plumbing clearly survives. This is only the outer wrapper, not proof the
  specific fan/health/ocsd/ocbb service IDs (5/6/7/8) still do real work on
  the receiving end.
- `health_fans`, `health_recv`, `health_service_request`, etc. strings exist
  in every version, but they live in `.json_dsp.elf.data` / trace back to
  the REST/Redfish "Thermal Configuration" feature (added 2.76), not the old
  SSH CLI's Health task. Presence of these strings is not evidence the old
  CLI-callable implementation survived -- this project's own 2.78 findings
  already showed identical help text with dead code behind it.
- Attempted to locate the receiving-side switch/dispatch table for service
  IDs 5-8 inside `.health.elf.text` via radare2 auto-analysis (`aaa`); no
  conclusive jump-table or registration-table structure found in the time
  spent. This specific question remains open.

**Verdict for now: inconclusive, not a clean A/B/C.** The 38KB loss is real
and consistent with "removed," but doesn't by itself prove the specific
service IDs are gone versus just-smaller-but-present. Further work here
needs either (a) a proper disassembler-grade function/xref graph of the
whole Health task (time-intensive even with r2), or (b) direct evidence
from real hardware.

## A promising, independently-useful lead: `patches/277-tools`
This repo already has an Airbus-Security-Lab-derived "tools" patch
(`patches/277-tools`) that replaces the CLI's `help` command with a live
memory-probe backdoor -- completely unrelated to the fan/health code path.
Checked whether its injection point (the `help`-handler function body,
1136 bytes) survives unchanged elsewhere:
- **Byte-identical** in 2.77, 2.78, 2.79, 2.80, 2.81.
- In 2.82, only **2 bytes differ**, both inside a `BL` immediate field (a
  called subroutine shifted slightly) -- not a structural change.

This means the memory-probe "tools" feature is a much lower-risk, high-value
candidate to port next: it doesn't depend on whatever happened to the
Health task, and once flashed + hardware-verified it would let live memory
on a real 2.80-2.82 unit be inspected directly -- which would answer the
open fan/health question with real evidence instead of more blind static
analysis. Its internal `BL` call targets (assembled with the same
"uniform-shift" convention as `fn_handler.S`) have **not yet** been
individually re-verified per target for 2.80-2.82, so it is not yet
considered build-ready.

## `tools.S` ported to 2.80/2.81/2.82 and built
`tools.S` doesn't use PC-relative `BL`s to external code at all -- every
external call (`GrabContext`, `printToShell`, `libc_malloc`, `libc_free`,
`sprintf`) goes through a local trampoline (`LDR R10, =literal; BX R10`)
defined inside the same assembled blob, so the only things that actually
needed re-verification per version were those 5 literal addresses:

- `GrabContext_fn` (0x21F9C) and `printToShell_fn` (0x12F68) -- these are the
  two actually load-bearing ones (used by the core read/write/execute probe
  and by every command's error path). Resolved each as a per-task
  "in-partition" address (the same `vaddr - 0x10000` convention documented
  in `2022-02-17-docs.md` for the CLI's command table) against
  `.ConAppCLI.elf.text`'s real section mapping, then disassembled the
  result: **byte-for-byte identical function prologues in all six firmware
  versions (2.77-2.82)**.
- `sprintf_fn`/`libc_malloc_fn`/`libc_free_fn` reference an address outside
  this firmware image's own file bounds entirely (true for 2.77 too --
  not something introduced by porting). Can't be statically verified either
  way for any version; the core probe functionality doesn't depend on them.

Built `patches/280-tools`, `patches/281-tools`, `patches/282-tools`
(signature bypass + the `help`->memory-probe hijack from `patches/277-tools`,
`tools.S` reused unmodified). Verified via the full pipeline: deterministic
across two builds each, `277-tools` regression build reconfirmed unaffected.
Also disassembled the actual injected bytes in the built 280-tools image and
confirmed: the code decodes cleanly through its real code/data boundary, the
local `BL` to the in-blob `GrabContext` trampoline lands correctly inside the
patch regardless of placement, and all 5 literal addresses plus all 5
expected format strings are present byte-for-byte unchanged.

**Still not hardware-tested.** This is the recommended next flash target
(after plain 2.80 signature-bypass-only) specifically because, once tested
working, it gives direct live-memory access to resolve the open fan/health
question below -- with real evidence instead of more static guessing.

## HARDWARE TEST RESULTS, 2026-11-05 (real HP DL380 Gen9)

**patches/280 (signature-bypass only): CONFIRMED WORKING.** Boots normally,
iLO reports correct version, SSH/web respond normally. First version beyond
2.77 confirmed on real hardware.

**patches/280-tools: CONFIRMED BROKEN.** Flashed clean (hash-verified, no
corruption in the flash itself -- `flash_ilo4` reported success). Result:
BIOS POST error 270 "iLO FW Communication Issue", iLO version read back as
255.255/0xFF.0xFF. A full AC power cycle did not resolve it. Recovered by
reflashing a clean (zero-patch) repack of the genuine 2.80 image, which
booted normally -- this rules out a repack/toolchain-level problem (the
pipeline correctly produces a flashable 2.80 image in general) and isolates
the cause specifically to this patch's content, not the version or the
build process.

### What this does and doesn't tell us
- Both the bootloader/kernel/userland signature-bypass bytes (shared with
  plain `patches/280`, independently confirmed working) are not the cause.
- The only new thing in `280-tools` is the 1136-byte `help`-handler
  replacement (`tools.S`). The defect is somewhere in that.

### A lead, not a confirmed cause: the help handler is referenced twice
Searched for all 4-byte references to the `help` handler's own address
elsewhere in `.ConAppCLI.elf.text` (not just the one command-table entry
point we already knew about). Found **two** references, 0x1C (28) bytes
apart -- consistent with `research/2022-02-17-docs.md`'s documented 28-byte
`shell_cmd` struct stride, meaning this function is used as a field (entry
point or a shared "generic help" callback) for **two** adjacent command-table
entries, not just `help`'s own. If anything calls into the OTHER command's
use of this same address with different argument conventions than `tools.S`
expects (it assumes it's always invoked as `help`'s own entrypoint with a
valid CLI context in R0), that could explain a crash reachable without a
user ever typing `help` over SSH -- potentially even during early
boot/self-test, which would fit the observed symptom (failure before SSH is
ever reachable).

**However**: checked 2.77 for the same pattern -- it has the **identical**
dual-reference structure (two refs, 28 bytes apart, at the equivalently
shifted offset). So this isn't something introduced by porting to 2.80; if
it's the cause, it would affect 2.77-tools equally.

### An important gap in the prior reasoning
The assumption that "this is fine, it's an existing/established patch" was
not actually verified -- there is **no documented hardware-test confirmation
of `patches/277-tools` anywhere in this repo** (checked `patches/277-tools/
readme.md` and `patches.md`; neither claims it). The technique being
"already in the repo" was treated as implicit validation, which was an
unjustified leap. It's entirely possible 277-tools has the same latent
defect and has simply never been tested on real hardware either.

### Recommended next diagnostic (not yet done)
Test `patches/277-tools` on this same DL380 Gen9 with genuine 2.77 firmware
before touching 280/281/282-tools again. This directly separates the two
remaining hypotheses:
- If 277-tools **also** fails the same way: the "overwrite `help`" technique
  itself is unsound in general, independent of version-porting work done
  here.
- If 277-tools **works**: something specific to the 2.80 port (the exact
  literal addresses, or something about this specific offset/version) is
  the real cause, and the dual-reference finding above becomes a much more
  likely explanation worth digging into further.

**Do not flash 280-tools, 281-tools, or 282-tools again until this is
resolved.**
