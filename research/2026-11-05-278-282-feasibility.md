# 2026-11-05: Feasibility pass on v2.78-v2.82

Picking up where `2022-02-19-onto-277.md` left off. Goal: figure out, with
actual evidence instead of inference, what's realistically portable to
2.78-2.82 beyond the "dead" 278/279 scaffolds already in this repo.

Tooling note: no IDA/Ghidra available this round. Used a Python3 venv with
`pyelftools` + `capstone` for static analysis, plus `radare2` for function-level
auto-analysis, instead of the Windows/IDA workflow described in earlier notes.
The python2 build/patch toolchain (`build.sh`, `util/patch.py`, keystone) ran
inside a Debian bullseye Docker container (host has no python2).

## Reproducibility gate
Rebuilt 2.77/2.78/2.79 from genuine HPE binaries and confirmed each output
matches the `RESULT_SHA1` already recorded in `patches/*/config`. Toolchain
trustworthy.

## Structural findings across all six binaries (2.77-2.82)
- Bootloader is **byte-identical** across all six versions.
- Kernel is identical 2.77->2.81. 2.82's kernel differs by only 89 scattered
  bytes, all inside embedded build-path strings (e.g. `...newpatch\...` ->
  `...ilo4_282\...`) -- cosmetic, explains the 6-byte overall file-size delta
  for 2.82.
- `elf.bin` is a real (if "stripped") ARM32 ELF with per-task sections
  (`.health.elf.text`, `.ConAppCLI.elf.text`, `.restserver.elf.text`, etc.),
  each with a real `sh_addr`/`sh_offset` pair -- i.e. pyelftools alone gives
  the vaddr<->file-offset mapping per task that the original research notes
  got from IDA + `dissection.rb`. No need to run the Ruby/metasm tool.

## Signature bypass: confirmed portable to 2.80/2.81/2.82
Bootloader (`0x38BC`) and kernel (`0x1FBB0`) checks are byte-identical in all
six firmwares -- same patch applies unmodified. The userland AOB
(`02 80 83 E0 87 1E 00 EB 00 20 B0 E1 1D 00 00 0A`) was found as a **unique
single match** in every version:
- 2.80 @ file offset `0x964DFC`
- 2.81 @ `0x969A0C`
- 2.82 @ `0x96A240`

Independently re-verified (not just AOB match) by disassembling the
surrounding ~24 bytes in each version and confirming the exact same
instruction shape as 2.77's known-good check: `BL <verify>; MOVS R2, R0; BEQ
<skip>`. All three match 2.77's pattern exactly.

Built `patches/280`, `patches/281`, `patches/282` with **signature-bypass
only** (reusing the identical bootloader/kernel patches, new userland
offsets above). Verified via the full pipeline: extract -> patch -> repack,
`build.sh <ver>` run twice each confirming deterministic output, hashes
recorded as `RESULT_SHA1` in each `config`. 2.77 regression build reconfirmed
unaffected. `BINARY_URL` in each new `config` is a placeholder
(`TODO-VERIFY-HPE-DOWNLOAD-URL`) -- real HPE download links need to be found
before these are considered complete; never guessed per project policy.

These three are **not yet hardware-tested** and are deliberately scoped to
just the unlock mechanism -- no fan/health code is touched.

## Fan/health/ocsd/ocbb: real evidence of code loss, not yet a clean "C" verdict
- The `.health.elf.text` section is **707,912 bytes in 2.77** and drops to
  roughly **670,600-670,750 bytes in every one of 2.78-2.82** (stable across
  that range, not a progressive decline). ~38KB of code genuinely
  disappeared between 2.77 and 2.78 and nothing comparable happened again
  through 2.82.
- The CLI-side `health_ipc_call` wrapper (the function `patches/277/asm/fn_handler.S`
  calls into) is **byte-identical** in 2.77/2.78/2.79 at the correctly
  shifted offset -- the generic "send an IPC request to another task"
  plumbing clearly survives. This is only the outer wrapper, not proof the
  specific fan/health/ocsd/ocbb service IDs (5/6/7/8) still do real work on
  the receiving end.
- `health_fans`, `health_recv`, `health_service_request`, etc. strings exist
  in every version, but they live in `.json_dsp.elf.data` / trace back to
  the REST/Redfish "Thermal Configuration" feature (added 2.76), not the old
  SSH CLI's Health task. Presence of these strings is not evidence the old
  CLI-callable implementation survived -- this project's own 2.78 findings
  already showed identical help text with dead code behind it.
- Attempted to locate the receiving-side switch/dispatch table for service
  IDs 5-8 inside `.health.elf.text` via radare2 auto-analysis (`aaa`); no
  conclusive jump-table or registration-table structure found in the time
  spent. This specific question remains open.

**Verdict for now: inconclusive, not a clean A/B/C.** The 38KB loss is real
and consistent with "removed," but doesn't by itself prove the specific
service IDs are gone versus just-smaller-but-present. Further work here
needs either (a) a proper disassembler-grade function/xref graph of the
whole Health task (time-intensive even with r2), or (b) direct evidence
from real hardware.

## A promising, independently-useful lead: `patches/277-tools`
This repo already has an Airbus-Security-Lab-derived "tools" patch
(`patches/277-tools`) that replaces the CLI's `help` command with a live
memory-probe backdoor -- completely unrelated to the fan/health code path.
Checked whether its injection point (the `help`-handler function body,
1136 bytes) survives unchanged elsewhere:
- **Byte-identical** in 2.77, 2.78, 2.79, 2.80, 2.81.
- In 2.82, only **2 bytes differ**, both inside a `BL` immediate field (a
  called subroutine shifted slightly) -- not a structural change.

This means the memory-probe "tools" feature is a much lower-risk, high-value
candidate to port next: it doesn't depend on whatever happened to the
Health task, and once flashed + hardware-verified it would let live memory
on a real 2.80-2.82 unit be inspected directly -- which would answer the
open fan/health question with real evidence instead of more blind static
analysis. Its internal `BL` call targets (assembled with the same
"uniform-shift" convention as `fn_handler.S`) have **not yet** been
individually re-verified per target for 2.80-2.82, so it is not yet
considered build-ready.

## `tools.S` ported to 2.80/2.81/2.82 and built
`tools.S` doesn't use PC-relative `BL`s to external code at all -- every
external call (`GrabContext`, `printToShell`, `libc_malloc`, `libc_free`,
`sprintf`) goes through a local trampoline (`LDR R10, =literal; BX R10`)
defined inside the same assembled blob, so the only things that actually
needed re-verification per version were those 5 literal addresses:

- `GrabContext_fn` (0x21F9C) and `printToShell_fn` (0x12F68) -- these are the
  two actually load-bearing ones (used by the core read/write/execute probe
  and by every command's error path). Resolved each as a per-task
  "in-partition" address (the same `vaddr - 0x10000` convention documented
  in `2022-02-17-docs.md` for the CLI's command table) against
  `.ConAppCLI.elf.text`'s real section mapping, then disassembled the
  result: **byte-for-byte identical function prologues in all six firmware
  versions (2.77-2.82)**.
- `sprintf_fn`/`libc_malloc_fn`/`libc_free_fn` reference an address outside
  this firmware image's own file bounds entirely (true for 2.77 too --
  not something introduced by porting). Can't be statically verified either
  way for any version; the core probe functionality doesn't depend on them.

Built `patches/280-tools`, `patches/281-tools`, `patches/282-tools`
(signature bypass + the `help`->memory-probe hijack from `patches/277-tools`,
`tools.S` reused unmodified). Verified via the full pipeline: deterministic
across two builds each, `277-tools` regression build reconfirmed unaffected.
Also disassembled the actual injected bytes in the built 280-tools image and
confirmed: the code decodes cleanly through its real code/data boundary, the
local `BL` to the in-blob `GrabContext` trampoline lands correctly inside the
patch regardless of placement, and all 5 literal addresses plus all 5
expected format strings are present byte-for-byte unchanged.

**Still not hardware-tested.** This is the recommended next flash target
(after plain 2.80 signature-bypass-only) specifically because, once tested
working, it gives direct live-memory access to resolve the open fan/health
question below -- with real evidence instead of more static guessing.

## HARDWARE TEST RESULTS, 2026-11-05 (real HP DL380 Gen9)

**patches/280 (signature-bypass only): CONFIRMED WORKING.** Boots normally,
iLO reports correct version, SSH/web respond normally. First version beyond
2.77 confirmed on real hardware.

**patches/280-tools: CONFIRMED BROKEN.** Flashed clean (hash-verified, no
corruption in the flash itself -- `flash_ilo4` reported success). Result:
BIOS POST error 270 "iLO FW Communication Issue", iLO version read back as
255.255/0xFF.0xFF. A full AC power cycle did not resolve it. Recovered by
reflashing a clean (zero-patch) repack of the genuine 2.80 image, which
booted normally -- this rules out a repack/toolchain-level problem (the
pipeline correctly produces a flashable 2.80 image in general) and isolates
the cause specifically to this patch's content, not the version or the
build process.

### What this does and doesn't tell us
- Both the bootloader/kernel/userland signature-bypass bytes (shared with
  plain `patches/280`, independently confirmed working) are not the cause.
- The only new thing in `280-tools` is the 1136-byte `help`-handler
  replacement (`tools.S`). The defect is somewhere in that.

### A lead that turned out to be a dead end
Searched for all 4-byte references to the `help` handler's own address
elsewhere in `.ConAppCLI.elf.text`. Found two references, 28 bytes apart
(matching the documented `shell_cmd` struct stride) -- initially looked
like it might mean this function gets invoked from somewhere other than a
direct `help` command, possibly during boot/self-test. Traced both
references back to their owning command-table entries by name: they are
**`help`** and **`?`** -- i.e. `?` is just the standard CLI shorthand alias
for `help`, both pointing at the same handler. Completely mundane, and
doesn't explain a failure that happens before SSH is ever reachable (no
hidden internal caller, just two ordinary user-typable command names).
Also checked 2.77 for the same pattern -- identical structure there too, so
this was never version-specific to begin with. **This lead is ruled out.**

Separately worth noting: whatever is failing can't be a secondary
integrity/CRC check beyond the one signature check we already bypass --
`patches/280` (confirmed working) also modifies file content (3 bytes) and
boots fine, so content modification alone isn't rejected by anything else.
And it can't be "any overwritten command entrypoint gets invoked during
boot" as a general firmware behavior either -- `patches/278`/`279`'s
existing (committed, pre-existing) handler overwrite at a different command
slot is documented to boot fine, with only the *fan commands themselves*
failing when actively invoked, not boot itself. So whatever's wrong is
either specific to *this* function's content, or specific to overwriting
*this particular* command slot -- not a general property of the technique.
No further hypothesis has been confirmed by static analysis alone; this is
the point where real hardware data (testing 277-tools on genuine 2.77,
per below) is the more productive path to the real answer rather than more
guessing.

### An important gap in the prior reasoning
The assumption that "this is fine, it's an existing/established patch" was
not actually verified -- there is **no documented hardware-test confirmation
of `patches/277-tools` anywhere in this repo** (checked `patches/277-tools/
readme.md` and `patches.md`; neither claims it). The technique being
"already in the repo" was treated as implicit validation, which was an
unjustified leap. It's entirely possible 277-tools has the same latent
defect and has simply never been tested on real hardware either.

### Recommended next diagnostic (not yet done)
Test `patches/277-tools` on this same DL380 Gen9 with genuine 2.77 firmware
before touching 280/281/282-tools again. This directly separates the two
remaining hypotheses:
- If 277-tools **also** fails the same way: the "overwrite `help`" technique
  itself is unsound in general, independent of version-porting work done
  here.
- If 277-tools **works**: something specific to the 2.80 port (the exact
  literal addresses, or something about this specific offset/version) is
  the real cause, and the dual-reference finding above becomes a much more
  likely explanation worth digging into further.

**Do not flash 280-tools, 281-tools, or 282-tools again until this is
resolved.**

## patches/280 SSH access and live fan/thermal check, 2026-11-05
Logged into the real DL380 Gen9 over SSH (after working around the client
issue below) and confirmed the `hpiLO->` DMTF SMASH CLP shell directly.

**Correction to earlier assumption**: the stock `help` output here lists
only the documented command set (`help`, `show`, `create`, `delete`,
`load`, `reset`, `set`, `start`, `stop`, `cd`, `date`, `time`, `exit`,
`version`, `oemhp_ping`, `oemhp_loadSSHKey`, `oemhp_deleteSSHKey`, `POWER`,
`UID`, `ONETIMEBOOT`, `NMI`, `VM`, `LANGUAGE`, `VSP`, `TEXTCONS`,
`TESTTRAP`) -- none of `quit`/`VSP\R`/`DEBUG`/`NULL_CMD` (the four slots
this project's patches repurpose) appear in it. This is NOT evidence they
don't exist in the same shell/command table -- it's now confirmed
consistent with them being deliberately undocumented/hidden aliases that
the static `help` text simply doesn't enumerate (this is the first live
confirmation of that, previously only inferred from strings).

**Live fan/thermal data**: `/system1/fan1`-`fan6` (standard, unpatched CLP
targets, part of the 2.76+ "Thermal Configuration" feature identified
earlier via static analysis) all report `OperationalStatus=Ok`,
`HealthState=Ok`. Observed `DesiredSpeed` dropping from 40-50% to 15-27%
between two checks a few minutes apart -- normal automatic thermal
ramp-down as the system settled post-boot, not an anomaly. `show -a` on
these targets revealed nothing beyond the plain `show` output -- same
properties, same verb list (`cd version exit show`, notably **no `set`**).
So `DesiredSpeed` is read-only via this specific target, not a write-capable
control surface as hoped. Doesn't rule out `set` working on a different
target (e.g. `/system1` itself, or some aggregate thermal target) --
untested, and not attempted without deliberate decision given it'd be a
write operation on live hardware.

### SSH client incompatibility (separate from the bootloader/patch work)
Modern OpenSSH (10.x) clients fail against this iLO's embedded SSH server
(`mpSSH_0.2.1`, visible in the server's version banner) with "no matching
key exchange method found" -- it only offers legacy
`diffie-hellman-group14-sha1`/`diffie-hellman-group1-sha1` KEX and
`ssh-rsa`/`ssh-dss` host keys, all disabled by default in current OpenSSH.
Forcing them back on (`-o KexAlgorithms=+diffie-hellman-group14-sha1 -o
HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedKeyTypes=+ssh-rsa`) gets further
but a very new client (OpenSSH 10.5, tested) still gets disconnected by the
server mid-key-exchange -- a second, deeper incompatibility beyond the
deprecated algorithm list, likely in how a modern client constructs the
classical (non-EC) DH exchange versus what this ~2012-era embedded
implementation expects. An older client (OpenSSH 8.4p1, Debian bullseye)
completes the handshake correctly with the same flags. This is unrelated to
any of the patch work in this repo -- it would affect connecting to
genuine, unpatched iLO4 firmware just as much.

## patches/280-fan: a second, proven-safe injection point, hardware-tested
After `280-tools` (the `help`-command hijack) was confirmed broken on real
hardware with no identified cause, built `patches/280-fan`: a much smaller
patch reusing the *other* technique this project already has an established
safe track record for -- the `NULL_CMD` slot `patches/277`/`278`/`279`
already repurpose, renamed to `FAN` and wired to `health_ipc_call` with the
fan service ID, reusing `fn_handler.S` unmodified. Deliberately omitted the
stdout-capture patch to keep the surface minimal.

Before building, re-ran the same cross-reference check that (in hindsight)
should have been done more rigorously for the `help` patch: searched the
whole binary for any other reference to `NULL_CMD`'s name or its original
entrypoint address, beyond the one command-table slot being patched. Found
what initially looked like 5+1 extra hits, but traced all of them to
`.embmedia.elf.text` / `.json_dsp.elf.data` -- completely different task
modules, amid clearly unrelated string/integer table data. Structurally
these can't even be real cross-task references (in-partition addresses only
resolve within their own task's mapping), so these are coincidental 4-byte
collisions, not real callers. Worth noting: this exact kind of check also
came back clean for the `help` patch, which still failed for an
unidentified reason -- so a clean result here was treated as "no new red
flag found," not proof of safety.

### Hardware test, 2026-11-05: boots fine, but the fan command itself does nothing
`patches/280-fan` boots and behaves normally -- confirms this injection
point really is safer than the `help` slot, consistent with its track
record. However, `fan p 0 min 25` produced no confirmed effect.

Getting a clean answer took some work: an initial apparent positive result
(`DesiredSpeed` jumping from 15% to 54% right after the command) turned out
to be a red herring -- polling `show /system1/fan1` repeatedly with *no*
commands at all showed the exact same 15%/54% oscillation happening on its
own, a few seconds apart. This is almost certainly the `tickler`-style
periodic self-test this project's own `fan` command grammar documents
(briefly spinning fans to verify they haven't seized) -- pre-existing stock
behavior, unrelated to the patch, that simply hadn't been noticed before
because earlier checks were spaced minutes apart rather than seconds apart.

Resolved cleanly by using the stock BIOS `ThermalConfig` setting
(`MaximumCooling`) as a known, deterministic baseline -- confirmed via
Redfish/CLP to reliably pin `DesiredSpeed` at 100% with no oscillation.
With that pin active, `fan p 0 min 25` produced zero observable deviation.

**This is now a hardware-confirmed negative, not just a static inference**:
the fan service is non-functional on 2.80. Consistent with (and now
actual evidence for, not just circumstantial support of) the ~38KB Health
task code shrinkage already confirmed present identically across
2.78-2.82 -- so this almost certainly applies to 2.81/2.82 too, though not
yet separately hardware-tested there.

## Function-level bindiff, 2.77 vs 2.80 Health task, 2026-11-05
Requested after today's hardware test confirmed the fan service is dead on
2.80. Prior byte-level diffing was misleading (only a 60-byte common
prefix / 12-byte common suffix) because removing any code causes the
linker to shift everything after it, re-encoding ARM's relative branch
immediates even when the underlying logic is unchanged -- confirmed
directly: multiple sampled functions (the `health_ipc_call` wrapper and
two of its callees) are byte-for-byte identical in every respect except
cross-reference addresses between 2.77 and 2.80.

Did a proper function-level diff instead: used radare2 (`aaa`/`afl`) to get
function boundaries in both Health task blobs, then matched functions by a
normalized signature (the tuple of instruction mnemonics within each
function, which is stable under address shifting since ARM is fixed
4-byte instructions and only operand *values* change, not instruction
count/order).

**Result: 106 substantial functions (>=15 instructions each), totaling
~41KB, exist in 2.77 with no structurally-matching function anywhere in
2.80.** This closely corroborates the previously-known ~38.8KB module size
difference with real, specific, quantified removed-function evidence,
rather than just an aggregate size number.

Checked the largest candidates for identifying strings or obviously
fan/health-specific patterns -- none reference any strings, and spot
disassembly (the largest, 691 instructions at health-task in-partition
address `0x90788`) shows dispatch-like bounds-checking and struct
dereferencing, consistent with (but not conclusive proof of) being part of
a command/type-handling implementation. Did not attempt to trace backward
from the actual service-ID switch inside the Health task to confirm which
specific functions implemented IDs 5-8 (health/fan/ocsd/ocbb) -- that
switch itself was never reliably located (see earlier attempt in this same
file), and doing so now would be substantial additional effort that
wouldn't change today's already hardware-confirmed conclusion that the fan
service doesn't work.

**Bottom line**: this is now a well-evidenced, specific removal (106 named
functions/addresses, not just "38KB disappeared somewhere"), fully
consistent with the hardware test result. Backporting 2.77's Health module
into 2.80 (discussed and set aside earlier today, both for the plausible
security-fix-reintroduction risk and the cross-module ABI/size-mismatch
technical risk) would mean reintroducing specifically these 106 functions
and whatever vulnerabilities, if any, were addressed by removing them --
this bindiff doesn't change that risk calculus, just quantifies what would
actually be reintroduced.

## Characterizing the 106 removed functions, 2026-11-05
Found all callers of the 106 removed functions from anywhere in the whole
Health module (not just among themselves), by scanning every `bl`/`blx` in
a full linear disassembly pass. 13 of the 106 have a caller in surviving
(non-removed) code -- i.e. genuine entry points, not orphaned dead code.

**Found the actual CLI command registration block**: health-task
in-partition region `0x28100`-`0x28b00` is a sequence of near-identical
"parse the argument string into tokens, then call handler(count, tokens)"
trampolines -- textbook registration pattern for named debug/CLI
sub-commands. Four of these trampolines each call a different removed
function:
- `0x3a970` (+4 more functions in its cluster, 14,424 bytes total -- by far
  the single largest chunk of everything removed). Best-guess: `fan`,
  given it has documented by far the richest subcommand surface of the
  four services (info/g/t/h/p/pid/rate/ramp/hyst/desc/actn/debug/DIMM/
  DRIVE/MB/PECI per the README), consistent with being the largest handler.
- `0x5715c` (+1 more, 4,808 bytes)
- `0x73840` (+7 more, 2,492 bytes)
- `0x12878` (3,928 bytes, no internal-call cluster found)

Can't confidently map the latter three to `health`/`ocsd`/`ocbb`
specifically -- would need tracing each one's expected argument
count/format convention, which wasn't recoverable from the data available.
But four argument-parsing trampolines, each calling a distinct removed
handler, sized consistently with four distinct CLI subsystems, is a
strong structural match for exactly the four services this project
targets.

The other 9 externally-referenced removed functions (`0x337f8`, `0x44db8`,
`0x743fc`, `0x90788`, `0x9fa14`, `0xa08ec`, `0xa0ee0`, `0xaa5a4`) are called
from low-level, generic-looking code -- bounds checks, struct-size-indexed
table lookups, sensor-table iteration -- not CLI-specific. Likely shared
infrastructure utilities pulled along in the same dead-code-elimination
pass rather than part of the CLI handlers themselves.

The remaining ~93 of 106 have no identifiable caller at all (including
from each other, mostly) -- almost certainly internal helpers reachable
only from within the four handler clusters above, which is consistent
with why they were removed together but don't show up as independently
orphaned. Individually characterizing each would need tracing deep into
each handler cluster's own internal structure -- substantial further
effort, with no decompiler available to speed it up, and it wouldn't
change the already-certain, hardware-confirmed conclusion that the fan
service doesn't work on 2.80+.
